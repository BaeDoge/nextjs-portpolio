## Background

When schedules and work updates are scattered across chat messages, personal calendars, spreadsheets, and file folders, it becomes difficult to find information or understand who is working on what.

I built an internal web application to manage schedules and to-dos in one calendar and attach plans or deliverables to the related work items. The focus was not on building a large enterprise suite, but on bringing the information and navigation used repeatedly by the team into one place.

## Data Model and Request Flow

~~~text
User browser
      │
      ▼
FastAPI
      │
      ├── Calendar Events
      ├── Todo Items
      ├── Comments
      ├── Attachments
      └── User / Activity History
      │
      ▼
SQLite
  ├── users
  ├── events
  ├── todos
  ├── attachments
  ├── event_comments
  └── activity_logs
~~~

Schedules and to-dos are stored separately, while comments and attachments have their own records. This keeps each feature from becoming overly dependent on another feature's data structure. SQLite foreign keys and WAL mode are used, and the admin functions provide access to supported deletion history and activity records.

## Deployment and Security Scope

<CalloutBox type="warning">
  This is a lightweight tool intended for a trusted internal network. User identification currently uses a browser identifier and connection IP rather than account-based authentication. It does not provide organisation-wide SSO or a full role-based permission system. A public deployment would require additional authentication, authorisation, HTTPS, access controls, and backup policies.
</CalloutBox>

Because the application may contain work documents, access to the host and data directory must be protected, and backups should be managed separately. Before expanding it into an organisation-wide service, the identity and role model should be strengthened.

## AI-assisted Development and My Contribution

I defined the requirements around the team's actual scheduling and document-sharing workflow, then designed the data model and screens. As the team began using the initial version, I split new requests into features and added comments, attachments, a Kanban view, administrative history, and search.

AI tools helped turn requests into implementable tasks, review data structures and screen flows, and speed up repetitive coding and debugging. I checked whether the proposed changes fitted the existing data and operating model, and handled integration, revisions, and final behaviour checks.

## Takeaways

This project showed me that even a small internal tool needs a coherent data model once schedules, users, attachments, and change history are connected. Observing how the team actually works and improving the tool in small increments helped me develop a practical approach to internal application design and operation.
