## Background

The first requirement for our in-house band concert was a simple way to share the schedule, venue, members, and setlist. I started with that invitation page, but wanted the website to be more than a static announcement. The audience should be able to take part in the event, while organisers should have a practical way to review those interactions.

I added emoji cheers, questions, and after-party responses, along with a separate admin view for reviewing visitor activity and audience messages.

Live site: [BAND NIGHT](https://daeil-band.vercel.app)

<CalloutBox type="info">
  This project was planned and deployed for a real in-house band event. The primary access path is a QR code opened on a mobile browser, without requiring a separate app or an audience account.
</CalloutBox>

## User Flow

1. **Discover the event** — Visitors open the shared link or QR code and check the schedule, venue, members, and setlist.
2. **Take part** — They register a display name and leave emoji cheers, questions, or an after-party response.
3. **Manage the event** — Organisers use a separate dashboard to review visitor activity, cheers, questions, and RSVP responses.
4. **Keep the memories** — After the event, interactive features are retired and the page remains as a photo archive.

## Design Decisions

### Separating live-event behaviour from the archive

Before the concert, cheers, questions, and RSVP interactions are useful. After the event, those controls are no longer needed. I used the event end time to switch the page into an archive mode, keeping the remaining content available without relying on database requests.

### Keeping audience reads lightweight

A concert page may receive a burst of visitors at the same time. I moved cheer aggregation into a database function and made the public page request a consolidated result. Detailed information needed only by organisers stays in the admin view.

### Scope of visitor identification

<CalloutBox type="warning">
  Visitors are identified by a browser UUID rather than an account login. The same person may appear as a different visitor when using another device or a private browsing session. This is not a full account-authentication or identity-management system.
</CalloutBox>

## AI-assisted Development and My Contribution

I defined the requirements and user flows, designed the data structure, and used AI tools such as ChatGPT to compare UI approaches, reason through API flows, draft SQL changes, and investigate errors. I split evolving requirements into smaller features, integrated the changes into the existing application, and checked the results in mobile browsers and the deployed environment.

Rather than treating generated code as complete, I reviewed and adapted it to the existing architecture. I handled the planning, prioritisation, implementation, integration, deployment, and operational improvements.

## Takeaways

Even a small event website needs service-level thinking once visitors can interact with it and organisers depend on its data. The project gave me practical experience balancing new features with post-event behaviour, request volume, operational convenience, and the limits of lightweight visitor identification.
