## 상황

RAG용 임베딩 모델을 골라야 했습니다.
한국어 문서가 대부분이고, 일부 영어 기술 용어가 섞여 있는 데이터였습니다.

## 처음엔 벤치마크를 봤다

리더보드 상위 모델을 골라서 붙였습니다.
그런데 실제 검색 결과가 기대보다 안 좋았습니다.

문제는 벤치마크 데이터셋과 저희 데이터가 성격이 달랐다는 점입니다.
저희 문서는 약관·규정처럼 문장이 길고 형식적인데,
벤치마크는 뉴스나 일반 문장 위주였습니다.

## 자체 평가셋을 만들었다

실제 사용자 질문 50개를 뽑고,
각 질문에 대해 "이 청크가 나와야 한다"를 사람이 직접 라벨링했습니다.

반나절 걸렸는데, 이게 가장 잘 쓴 시간이었습니다.

그리고 Recall@5로 측정했습니다.
답이 상위 5개 안에 들어오는 비율입니다.
RAG에서는 순위 1등보다 "후보 안에 있는가"가 더 중요해서 이 지표를 골랐습니다.

## 확인한 것

**1. 다국어 모델이 유리했다**

문서에 `Kubernetes`, `HPA` 같은 영어 용어가 섞여 있었는데,
한국어 전용 모델은 이런 토큰을 잘 못 다뤘습니다.

**2. 차원이 크다고 좋진 않았다**

1024차원 모델과 384차원 모델의 Recall@5 차이가 크지 않았습니다.
반면 저장 용량과 검색 지연은 눈에 띄게 차이 났습니다.

**3. 정규화를 빠뜨리면 안 된다**

코사인 유사도를 쓸 거면 임베딩을 정규화해야 합니다.
이걸 안 해서 초반에 결과가 이상했습니다.

```python
output = model(text, pooling="mean", normalize=True)
```

`normalize=True` 한 줄입니다. 빠뜨리기 쉽습니다.

## 결론

최종적으로 384차원 다국어 모델을 골랐습니다.
리더보드 순위는 낮았지만 저희 데이터에서는 더 잘 맞았고, 훨씬 가벼웠습니다.

**자기 데이터로 만든 평가셋 50개가 리더보드보다 유용합니다.**
만드는 데 반나절이면 충분합니다.
