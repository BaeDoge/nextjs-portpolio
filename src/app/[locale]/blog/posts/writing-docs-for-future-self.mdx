## 계기

작년에 만든 배치를 손볼 일이 있었습니다.
코드는 제가 짰는데 왜 이렇게 했는지 기억이 안 났습니다.

특히 이런 부분이 곤란했습니다.

```python
if retry_count > 3 and elapsed < 60:
    time.sleep(5)
```

숫자 3, 60, 5가 어디서 나온 건지 알 수 없었습니다.
바꿔도 되는지 판단할 근거가 없으니 결국 손을 못 댔습니다.

## 규칙 1 — 숫자에는 근거를 적는다

```python
# 외부 API가 분당 60회로 제한. 3회 이상 연속 실패하면
# 레이트리밋일 가능성이 높아 5초 쉬었다 재시도한다.
# (5초는 실측 기준 회복에 걸린 평균 시간)
if retry_count > 3 and elapsed < 60:
    time.sleep(5)
```

코드를 보면 "무엇"은 알 수 있습니다. 주석은 **"왜"**를 적는 자리입니다.

## 규칙 2 — 안 한 선택을 적는다

```python
# 큐(SQS)를 쓰는 것도 검토했으나, 일 300건 수준이라
# 운영 복잡도 대비 이득이 없다고 판단해 DB 폴링으로 감.
# 건수가 크게 늘면 재검토할 것.
```

이게 가장 유용했습니다.
나중에 "왜 큐를 안 썼지?"라는 질문에 바로 답이 됩니다.
검토를 다시 하지 않아도 됩니다.

## 규칙 3 — README에 "어떻게 돌리는가"를 맨 위에

정작 필요할 때 찾는 건 아키텍처 설명이 아니라
"로컬에서 어떻게 띄우지"입니다.

```markdown
## 로컬 실행

1. `cp .env.example .env` 후 값 채우기
2. `docker compose up -d db`
3. `python -m app.migrate`
4. `uvicorn app.main:app --reload`

문제가 생기면: 대부분 3번에서 DB가 아직 안 떠 있어서입니다. 10초 뒤 재시도.
```

마지막 줄 같은 게 실제로 시간을 아껴줍니다.

## 규칙 4 — 임시방편은 임시라고 쓴다

```python
# [임시] 2025-09-12
# 상대 API가 500을 던지는 문제가 해결될 때까지만 재시도로 버팀.
# 담당자 회신 오면 제거할 것.
```

날짜를 적어두면 "이게 언제부터 임시였나"를 알 수 있습니다.
2년 된 임시 코드는 사실 영구 코드입니다.

## 정리

문서를 잘 쓰려고 하기보다, **미래의 내가 물어볼 질문**에 미리 답해두는 쪽이 현실적이었습니다.
질문은 보통 정해져 있습니다. 왜 이렇게 했나, 바꿔도 되나, 어떻게 돌리나.
