오늘은 코드 문서화와 관련해 정리한 원칙을 공유해 보겠습니다.

## 계기

작년에 작성한 배치 코드를 수정할 일이 있었는데, 작성 당시의 의도를 파악하기 어려운 부분이 있었습니다.

```python
if retry_count > 3 and elapsed < 60:
    time.sleep(5)
```

3, 60, 5라는 수치의 근거가 남아있지 않아, 수정 가능 여부를 판단하기 어려웠습니다.

## 원칙 1 — 수치에는 근거를 남긴다

```python
# 외부 API가 분당 60회로 제한됨. 3회 이상 연속 실패 시
# 레이트리밋 가능성이 높아 5초 대기 후 재시도.
# (5초는 실측 기준 평균 회복 시간)
if retry_count > 3 and elapsed < 60:
    time.sleep(5)
```

## 원칙 2 — 채택하지 않은 방안도 기록한다

```python
# 큐(SQS) 도입도 검토했으나, 일 300건 수준에서는
# 운영 복잡도 대비 이점이 낮다고 판단해 DB 폴링 방식으로 결정.
# 처리량 증가 시 재검토 필요.
```

## 원칙 3 — README 상단에 실행 방법을 명시한다

```markdown
## 로컬 실행

1. `cp .env.example .env` 후 값 입력
2. `docker compose up -d db`
3. `python -m app.migrate`
4. `uvicorn app.main:app --reload`

문제 발생 시: 대부분 3번 단계에서 DB 기동 전 실행되어 발생합니다. 10초 후 재시도하세요.
```

## 원칙 4 — 임시 조치는 날짜와 함께 명시한다

```python
# [임시] 2025-09-12
# 외부 API 500 에러 대응을 위한 재시도 로직.
# 담당자 회신 후 제거 예정.
```

날짜를 기록해두면 해당 조치가 유지된 기간을 확인할 수 있습니다.

## 결론

문서화의 핵심은 형식을 갖추는 것보다, 이후에 발생할 질문에 미리 답을 남겨두는 것이었습니다. 왜 이렇게 구현했는지, 수정해도 되는지, 어떻게 실행하는지 — 이 세 가지가 가장 빈번하게 필요한 정보였습니다.
