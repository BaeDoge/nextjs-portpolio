## Symptom

A query endpoint suddenly took over three seconds.
The column definitely had an index on it.

## Start with EXPLAIN

```sql
EXPLAIN SELECT * FROM chat_logs
WHERE DATE(created_at) = '2026-03-20';
```

```
type: ALL
key: NULL
rows: 2841203
```

`key: NULL`. The index isn't used at all.

## Cause — the column is wrapped in a function

Wrapping an indexed column in a function like `DATE(created_at)` **disables the index**.
MySQL has to pull `created_at` from every row and run `DATE()` on it.

## The fixed query

Switch to a range condition:

```sql
SELECT * FROM chat_logs
WHERE created_at >= '2026-03-20 00:00:00'
  AND created_at <  '2026-03-21 00:00:00';
```

```
type: range
key: idx_created_at
rows: 4210
```

3s → 40ms.

I use `>= start, < next day` rather than
`BETWEEN '... 00:00:00' AND '... 23:59:59'` because sub-second values like
23:59:59.5 fall outside the latter. The range form is safer.

## Easy ways to make the same mistake

```sql
-- No index
WHERE YEAR(created_at) = 2026
WHERE CAST(user_id AS CHAR) = '123'
WHERE user_id + 0 = 123

-- Index used
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE user_id = 123
```

Passing a number to a string column triggers a silent cast that kills the index too.
Match the types.

## Habit

When something slows down, don't guess — run `EXPLAIN`.
Checking whether `key` is NULL and whether `rows` is wildly larger than the result set
catches most cases.
