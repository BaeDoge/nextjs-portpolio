Today I'll write up how I improved the way I write code review comments.

## Problem

My review comments often didn't lead to actual changes. Looking back at them, they looked like this:

```
I think this will cause N+1
```

The issue I pointed out was correct, but it didn't say where the problem was, why it was a problem, or how to fix it.

## The format I switched to

I changed comments to include three things.

**1. Where the problem is**

```
Accessing user.profile inside this loop runs a query on every iteration.
With 100 items, that's 101 queries.
```

**2. The possible impact**

```
The list is short now, so the problem isn't visible,
but the admin screen can load up to 500 rows, which could cause delays.
```

**3. A direction for the fix**

```
Applying select_related("profile") handles it in one query.
```

## Adding labels

I added labels to separate the priority of comments.

- `[must]`: must be fixed before merge
- `[nit]`: optional
- `[question]`: a question to confirm something

After adding labels, unnecessary arguments over minor remarks decreased.

## Conclusion

Writing the problem, the impact, and a direction for the fix together raised how often comments were applied. For changes that need structural discussion, I talk directly instead of leaving comments.
