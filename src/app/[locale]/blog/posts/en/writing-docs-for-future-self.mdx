Today I'll share the principles I settled on for documenting code.

## What started it

I had to modify batch code I wrote last year, and there were parts where I couldn't tell what I had intended at the time.

```python
if retry_count > 3 and elapsed < 60:
    time.sleep(5)
```

The reasons for the numbers 3, 60, and 5 were not recorded, so I couldn't judge whether it was safe to change.

## Principle 1: Leave the reason for numbers

```python
# The external API is limited to 60 calls per minute. After 3 or more
# consecutive failures, rate limiting is likely, so wait 5 seconds and retry.
# (5 seconds is the average recovery time I measured)
if retry_count > 3 and elapsed < 60:
    time.sleep(5)
```

## Principle 2: Record the options I didn't choose

```python
# I also considered introducing a queue (SQS), but at about 300 items per day
# the benefit looked low compared to the operational complexity, so I chose
# DB polling. Revisit if throughput grows.
```

## Principle 3: Put how to run it at the top of the README

```markdown
## Run locally

1. Copy `.env.example` to `.env` and fill in the values
2. `docker compose up -d db`
3. `python -m app.migrate`
4. `uvicorn app.main:app --reload`

If something goes wrong: it is usually step 3 running before the DB is up. Retry after 10 seconds.
```

## Principle 4: Date temporary workarounds

```python
# [Temporary] 2025-09-12
# Retry logic for handling 500 errors from the external API.
# To be removed after the owner replies.
```

With a date recorded, you can see how long the workaround has been in place.

## Conclusion

What mattered in documentation was not the format but leaving answers to the questions that would come later. Why it was implemented this way, whether it's safe to change, and how to run it were the three things needed most often.
