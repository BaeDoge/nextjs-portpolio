Today I'll write up a case where using `async def` in FastAPI did not improve performance.

## Situation

To increase concurrent throughput, I changed every handler to `async def`. Throughput barely changed, and some paths actually got slower.

## Cause

```python
import requests

@app.get("/items")
async def get_items():
    # requests is a synchronous library
    res = requests.get("https://api.example.com/items")
    return res.json()
```

I was making a synchronous, blocking call inside `async def`. That stalls the whole event loop, so no other request is handled in the meantime.

## Fix

**1. Switch to an async client**

```python
import httpx

@app.get("/items")
async def get_items():
    async with httpx.AsyncClient() as client:
        res = await client.get("https://api.example.com/items")
    return res.json()
```

**2. Delegate to a thread pool when switching isn't possible**

```python
from fastapi.concurrency import run_in_threadpool

@app.get("/report")
async def get_report():
    data = await run_in_threadpool(legacy_sync_call)
    return data
```

**3. Move CPU-bound work to a separate process**

CPU-heavy work such as image processing did not improve even with a thread pool, so I moved it to a separate worker process.

## Conclusion

If there is nothing to `await`, there is no reason to use `async def`, and blocking calls must not be made inside it. When blocking is unavoidable, wrapping the call in `run_in_threadpool` is the safe option.
