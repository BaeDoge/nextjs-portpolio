Today I'll write up how I improved the way I record technical debt.

## Problem

```python
# TODO: add caching later
# FIXME: temporary workaround
```

I left many comments like these, but when I looked back later, no background was left, so it was hard to tell whether they still needed to be handled.

## Attempt 1: Convert them to issues

I converted everything into GitHub issues, but without priorities they were pushed aside by new feature work and never handled.

## Attempt 2: Add context to the comment

```python
# [Debt] 2025-11-20 / Seung Ho Bae
# Situation: handled with a synchronous call because of the schedule
# Impact: may time out as requests increase. Currently about 300 per day
# Condition: switch to a queue structure above 1,000 per day
```

By stating the condition for handling it, I could leave the basis for the decision in the code.

## Attempt 3: Manage it in a separate document

```markdown
| Item | Condition | Impact | Recorded |
|---|---|---|---|
| Synchronous file processing | Above 1,000/day | Timeout | 2025-11-20 |
| Hardcoded categories | When a new category is requested | Needs a deploy | 2025-10-02 |
```

I review it every quarter and pick items whose conditions have been met as the first to handle.

## Conclusion

I concluded that it is more realistic to treat technical debt as something to manage than something to eliminate completely. Stating the condition for handling it was effective in leaving a basis for decisions.
