Today I'll write up a batch error caused by a missing time zone setting.

## Situation

An aggregation batch that runs at midnight every day was missing some of the previous day's data. It worked fine in my local environment.

## Cause

```python
from datetime import datetime, timedelta

today = datetime.now().date()
yesterday = today - timedelta(days=1)
```

`datetime.now()` follows the local time zone of the environment it runs in. My local environment was KST, but the container in the deployment environment was set to UTC.

As a result, even when the batch ran at 00:30 Korean time, it was 15:30 of the previous day by the container's clock, so `yesterday` was off by one day.

## Fix

I specified the time zone explicitly.

```python
from datetime import datetime, timedelta
from zoneinfo import ZoneInfo

KST = ZoneInfo("Asia/Seoul")

today = datetime.now(KST).date()
yesterday = today - timedelta(days=1)
```

I also set the time zone in the container's environment variables.

```dockerfile
ENV TZ=Asia/Seoul
```

## Preventing a repeat

I restricted the use of `datetime.now()` and `datetime.utcnow()` with a lint rule.

```python
# Not allowed
datetime.now()
datetime.utcnow()

# Allowed
datetime.now(KST)
datetime.now(timezone.utc)
```

## Conclusion

This was a case where a difference between the local and deployment environments had been implicitly baked into the code. For environment-dependent things like time zones, encodings, and path separators, it is safer to specify them explicitly.
