Today I'll write up a problem I ran into while using FastAPI's `BackgroundTasks`.

## Situation

I used `BackgroundTasks` to handle post-processing such as parsing and embedding asynchronously after a file upload.

```python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()

@app.post("/upload")
async def upload(file: UploadFile, bg: BackgroundTasks):
    path = await save_file(file)
    bg.add_task(process_document, path)
    return {"status": "accepted"}
```

It worked fine in local testing.

## Problem

After deploying, only about half of the documents had been processed. There were no error logs, and every API response was 200.

Comparing against the deploy logs, the lost jobs lined up with the times of redeploys and scale-ins.

## Cause

There were two causes.

**1. Jobs are lost when a worker restarts**

`BackgroundTasks` runs in the same process that returned the response. If the process ends because of a deploy, scale-in, or OOM, pending jobs disappear without any record.

**2. Weak exception handling**

```python
def process_document(path: str):
    # Even if an exception is raised here, the client has already received 200
    ...
```

Without separate logging, there was no way to know whether a job had failed.

## Fix

I changed the structure so that job state is recorded in the DB and a separate worker processes pending jobs.

```python
@app.post("/upload")
async def upload(file: UploadFile):
    path = await save_file(file)
    await db.execute(
        "INSERT INTO jobs (type, payload, status) VALUES (?, ?, 'pending')",
        ("process_document", path),
    )
    return {"status": "queued"}
```

After this change I could check processing status directly with a query, so finding the cause got faster even when the same problem came up.

## Conclusion

I concluded that `BackgroundTasks` is only appropriate for short jobs that can fail without harm. Jobs that must not be lost are safer designed on a queue or DB-based structure from the start.
