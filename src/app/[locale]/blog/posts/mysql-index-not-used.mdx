## 증상

조회 API가 갑자기 느려졌습니다. 3초가 넘어갔습니다.
해당 컬럼에 인덱스는 분명히 걸려 있었습니다.

## EXPLAIN부터

```sql
EXPLAIN SELECT * FROM chat_logs
WHERE DATE(created_at) = '2026-03-20';
```

```
type: ALL
key: NULL
rows: 2841203
```

`key: NULL`. 인덱스를 안 탑니다.

## 원인 — 컬럼을 함수로 감쌌다

`DATE(created_at)`처럼 **인덱스 컬럼에 함수를 씌우면** 인덱스를 못 씁니다.
MySQL 입장에서는 모든 행의 `created_at`을 꺼내서 `DATE()`를 돌려봐야 하니까요.

## 고친 쿼리

범위 조건으로 바꿨습니다.

```sql
SELECT * FROM chat_logs
WHERE created_at >= '2026-03-20 00:00:00'
  AND created_at <  '2026-03-21 00:00:00';
```

```
type: range
key: idx_created_at
rows: 4210
```

3초 → 40ms.

`BETWEEN '2026-03-20 00:00:00' AND '2026-03-20 23:59:59'` 대신
`>= 시작, < 다음날`을 쓴 이유는 초 단위 아래(밀리초)가 있을 때
23:59:59.5 같은 값이 빠지기 때문입니다. 이쪽이 안전합니다.

## 같은 실수를 하기 쉬운 패턴들

```sql
-- 안 탐
WHERE YEAR(created_at) = 2026
WHERE CAST(user_id AS CHAR) = '123'
WHERE user_id + 0 = 123

-- 탐
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE user_id = 123
```

문자열 컬럼에 숫자를 넣는 경우도 조용히 형변환이 일어나서 인덱스를 날립니다.
타입은 맞춰서 넣는 게 좋습니다.

## 습관

느려지면 추측하지 말고 `EXPLAIN`부터 봅니다.
`key`가 NULL인지, `rows`가 실제 결과보다 터무니없이 큰지 두 가지만 봐도 대부분 잡힙니다.
