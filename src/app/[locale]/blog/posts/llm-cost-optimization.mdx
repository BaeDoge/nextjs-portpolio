## 발견

사내 도구 하나의 LLM API 비용이 예상보다 훨씬 높게 나왔습니다.
호출 수는 예상대로였는데 토큰이 많았습니다.

## 1. 시스템 프롬프트가 매번 들어간다

당연한 얘기인데 간과하기 쉽습니다.
시스템 프롬프트가 1,500 토큰이면, 호출 1만 건에 1,500만 토큰입니다.
**대화 내용과 무관하게** 나갑니다.

프롬프트를 다시 읽어보니 이런 게 있었습니다.

```
당신은 매우 친절하고 전문적이며 정확한 어시스턴트입니다.
사용자의 질문에 성심성의껏 답변해야 하며...
```

이런 수식어는 출력 품질에 거의 영향이 없었습니다. 지웠습니다.
1,500 → 400 토큰. 품질 차이는 체감되지 않았습니다.

## 2. 대화 히스토리를 전부 보냈다

멀티턴 대화에서 히스토리를 통째로 넣고 있었습니다.
턴이 쌓일수록 토큰이 선형으로 늘어납니다.

최근 N턴만 유지하도록 바꿨습니다.

```python
MAX_TURNS = 6

def trim(messages: list[dict]) -> list[dict]:
    system = [m for m in messages if m["role"] == "system"]
    rest = [m for m in messages if m["role"] != "system"]
    return system + rest[-MAX_TURNS * 2:]
```

긴 대화가 필요한 경우엔 앞부분을 요약해서 한 메시지로 접는 방법도 있는데,
저희 쓰임새에선 최근 턴만으로 충분했습니다.

## 3. RAG 컨텍스트가 과했다

`match_count=10`으로 상위 10개 청크를 넣고 있었습니다.
로그를 보니 실제 답변에 인용되는 건 보통 2~3개였습니다.

`match_count=4`로 줄이고, 유사도 임계값을 올렸습니다.
답변 품질은 오히려 좋아졌습니다. 관련 없는 청크가 섞이면 모델이 헷갈립니다.

## 4. 모델을 나눴다

모든 요청에 가장 큰 모델을 쓰고 있었습니다.
분류나 짧은 요약 같은 단순 작업은 작은 모델로 충분했습니다.

```python
def pick_model(task: str) -> str:
    if task in ("classify", "summarize_short"):
        return SMALL_MODEL
    return LARGE_MODEL
```

## 결과

월 비용이 약 60% 줄었습니다.
가장 효과가 컸던 건 1번(시스템 프롬프트)과 3번(컨텍스트 축소)이었습니다.

## 교훈

비용 문제는 대개 "호출이 많아서"가 아니라 **"한 번에 너무 많이 보내서"**입니다.
토큰 사용량을 호출별로 로깅해두면 어디가 무거운지 바로 보입니다.
저는 이걸 안 해둬서 한참 헤맸습니다.
