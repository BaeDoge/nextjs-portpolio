## 처음엔 그냥 512로 잘랐다

RAG 튜토리얼을 보면 대부분 `chunk_size=512, overlap=50` 정도로 시작합니다.
저도 그렇게 시작했고, 데모까지는 잘 됐습니다.

문제는 실제 약관 문서를 넣었을 때였습니다.

## 문제 1 — 조항이 잘린다

약관은 이렇게 생겼습니다.

```
제15조 (해지)
① 고객은 언제든지 계약을 해지할 수 있습니다.
② 제1항에도 불구하고, 다음 각 호의 경우에는 해지가 제한됩니다.
   1. ...
   2. ...
```

512 토큰으로 자르면 ①과 ② 사이에서 잘리는 경우가 생깁니다.
그러면 "해지할 수 있다"만 검색되고 "제한된다"는 안 나옵니다.
금융 도메인에서 이건 단순 품질 문제가 아니라 사고입니다.

## 시도 1 — overlap을 키웠다

`overlap=200`까지 올려봤습니다. 잘림은 줄었는데 인덱스 크기가 늘고,
같은 내용이 여러 청크에 중복되면서 검색 결과 상위권을 비슷한 청크가 채우는 문제가 생겼습니다.

## 시도 2 — 조항 단위로 잘랐다

정규식으로 `제N조`를 기준으로 나눴습니다.

```python
import re

def split_by_article(text: str) -> list[str]:
    parts = re.split(r'(제\s*\d+\s*조)', text)
    chunks = []
    for i in range(1, len(parts), 2):
        chunks.append(parts[i] + parts[i + 1])
    return chunks
```

의미 단위는 지켜졌지만 이번엔 길이 편차가 문제였습니다.
어떤 조는 2줄, 어떤 조는 3페이지입니다. 긴 조항은 임베딩이 뭉개집니다.

## 결국 — 2단계로 나눴다

1. 먼저 조항 단위로 자른다 (의미 경계 보존)
2. 조항이 너무 길면 항(①②③) 단위로 다시 자른다
3. 각 청크 앞에 **부모 조항 제목을 붙인다**

3번이 핵심이었습니다.

```
[제15조 (해지)] ② 제1항에도 불구하고, 다음 각 호의 경우에는...
```

이렇게 하니 청크가 잘려도 맥락이 남습니다.
검색 정확도도 눈에 띄게 올라갔습니다.

## 배운 것

청킹은 "몇 토큰"의 문제가 아니라 **"이 문서의 의미 단위가 무엇인가"**의 문제입니다.
약관은 조항, 회의록은 안건, 코드는 함수. 도메인마다 답이 다릅니다.

튜토리얼의 512는 "일반 문서일 때의 기본값"이지 정답이 아니었습니다.
