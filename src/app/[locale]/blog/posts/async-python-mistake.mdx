오늘은 FastAPI에서 `async def`를 사용했음에도 성능이 개선되지 않았던 사례를 정리해 보겠습니다.

## 상황

동시 처리량을 높이기 위해 핸들러를 전부 `async def`로 변경했습니다. 결과적으로 처리량은 거의 변화가 없었고, 일부 구간은 오히려 느려졌습니다.

## 원인

```python
import requests

@app.get("/items")
async def get_items():
    # requests는 동기 라이브러리
    res = requests.get("https://api.example.com/items")
    return res.json()
```

`async def` 내부에서 동기 방식의 블로킹 호출을 사용하고 있었습니다. 이 경우 이벤트 루프 전체가 멈추기 때문에, 그동안 다른 요청은 처리되지 않습니다.

## 해결

**1. 비동기 클라이언트로 교체**

```python
import httpx

@app.get("/items")
async def get_items():
    async with httpx.AsyncClient() as client:
        res = await client.get("https://api.example.com/items")
    return res.json()
```

**2. 교체가 어려운 경우 스레드풀로 위임**

```python
from fastapi.concurrency import run_in_threadpool

@app.get("/report")
async def get_report():
    data = await run_in_threadpool(legacy_sync_call)
    return data
```

**3. CPU 바운드 작업은 별도 프로세스로 분리**

이미지 처리와 같이 CPU를 많이 사용하는 작업은 스레드풀로도 개선되지 않아 별도 워커 프로세스로 분리했습니다.

## 결론

`await`할 대상이 없다면 `async def`를 사용할 이유가 없으며, `async def` 내부에서 블로킹 호출을 하지 않아야 한다는 점을 확인했습니다. 블로킹이 불가피한 경우 `run_in_threadpool`로 감싸는 것이 안전합니다.
